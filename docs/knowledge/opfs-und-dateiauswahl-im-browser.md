# Game data in the browser: file selection, OPFS and WasmFS

Status 2026-10-11 (P6.1). Applies to every recomp project that must read data from its own dump in the browser without
putting it on a server. Code: `platform/web/` (`lgp_platform_web`, `lgp_add_web_page()`), tests in
`tests/web/` (`ctest -L web`, in the WASM build `-L browser`).

## Flow

1. The page (`platform/web/game.html.in`, generated by `lgp_add_web_page()`) offers a folder picker
   (`<input type=file webkitdirectory>`). The user picks the folder that `tools/extract` writes
   (`exefs/`, `romfs/`).
2. `lgp_web.js` decides per file whether and where it goes (`classify`): `exefs/…`, `romfs/…`, `systemdata/…`,
   `romfs.bin` and module names (`main`, `sdk`, `subsdk*`, `rtld`, `main.npdm`, `*.nso`/`*.nro`) directly in the chosen
   folder. Everything else is left alone, explicitly including NSP, NCA and key files. A folder of the same name deeper in
   the RomFS (e.g. `romfs/…/exefs/`) stays in the RomFS: the first section name from the top counts.
3. A worker (`opfs_copy_worker.js`) copies the files in 8 MiB chunks into the Origin Private File System
   (OPFS) under `lgp/data/`. A new import replaces `lgp/data/` entirely; `lgp/save/` stays.
4. Only "Start" loads `<programm>.js`. The program mounts OPFS via WasmFS under `/opfs` and reads everything with
   normal file functions: `--exefs /opfs/lgp/data/exefs --game /opfs/lgp/data --save /opfs/lgp/save`.

The data never leaves the computer: OPFS is a private browser storage per origin, not visible in the normal
file system and unreachable for other pages. Another port on `localhost` is another origin;
a new import is needed there.

## Browser facts that shape the design

- **Synchronous OPFS access exists only in workers.** `FileSystemSyncAccessHandle` (`createSyncAccessHandle()`)
  exists only in dedicated workers. That is why a worker copies, not the page. Advantage over
  `createWritable()`: no temporary shadow-copy swap, which matters for several GiB of RomFS. Supported in Chrome,
  Firefox (from 111) and Safari (from 15.2, writing reliable from 17).
- **A sync handle locks the file.** The program must not run during the copy; the page disables "Start"
  while copying.
- **`File` objects are transferable.** The chosen files go to the worker via `postMessage`; they are read
  in pieces with `file.slice(a, b).arrayBuffer()`, never the whole file at once.
- **Storage space:** check `navigator.storage.estimate()` before the copy (quota minus usage plus what the
  import replaces) and request `navigator.storage.persist()`. Without "persistent" the browser may delete the data when
  space runs short; the page then says so in the log.
- **`webkitdirectory`** works in all three engines and provides `webkitRelativePath` with the name of the chosen
  folder as the first part. `showDirectoryPicker()` exists only in Chromium, hence not used.
- **Threads need cross-origin isolation** (COOP/COEP headers, `tools/web/serve.py`). Without it there is no
  `SharedArrayBuffer`, and Emscripten pthreads do not start.

## Emscripten: WasmFS with OPFS backend

- Link with `-sWASMFS=1` (`lgp_platform_web` makes it a PUBLIC link option), then
  `wasmfs_create_opfs_backend()` and `wasmfs_create_directory("/opfs", 0777, backend)`. WasmFS replaces the
  JS file system of the whole program; programs without OPFS stay with the old FS (NODERAWFS in the Node tests).
- **Do not mount from the browser main thread.** The backend works through its own worker thread and blocks on
  creation until that thread runs. Under `PROXY_TO_PTHREAD` `main()` runs on a pthread, where it works. A global
  constructor would instead run on the main thread. That is why `lgp::boot::prepare_host()` (boot program) or
  `lgp::platform::web::mount_opfs()` mounts at the beginning of `main()`.
- Every file access is forwarded to the OPFS worker (one thread switch per `read`). For performance (P6.3):
  larger read chunks or our own cache.
- The OPFS backend **cannot rename directories**, only files. WasmFS returns `EBUSY`
  (`insertMove` in `opfs_backend.cpp`), `HostDirectoryStorage` turns it into `Io`; `browser.opfs_storage` prints the
  value. In that case fsp-srv copies and deletes the source, and the save journal works without
  renaming folders (see [`horizon-fsp-srv-romfs.md`](horizon-fsp-srv-romfs.md)).
- A file with an open `FileSystemSyncAccessHandle` is locked: `getFile()`, deleting and moving
  fail. Whether WasmFS only holds such handles while the program has the file open has not been checked.
- `std::filesystem` (and thus `HostDirectoryStorage`) works unchanged on WasmFS; the OPFS backend is
  therefore just a mount plus `HostDirectoryStorage` on top (`open_opfs_storage`).

## Backing up saves (P5.3)

- Saves live only in the OPFS of this browser and this origin. "Delete saves", deleting the site data
  or another port loses them. The page therefore offers **Export saves** (ZIP download) and **Import saves…**
  (choose a ZIP).
- The export contains per save only the committed state, in the neutral layout
  `<program>/account/<uid>/savedata.bin`, i.e. as the game sees it. So the file can also be opened with tools
  or placed under `--save` on the desktop. `savesForExport` in `lgp_web.js` reads `.lgp-journal`
  (or `.tmp`) for that, like the runtime.
- The import replaces `lgp/save` entirely (after asking), via the same copy worker as the game data. It accepts
  stored and deflate-compressed ZIPs (`DecompressionStream('deflate-raw')`, as written by Explorer, Finder or
  `zip`), checks paths like `normalize_path` and the CRC. A common top-level folder is removed. A
  damaged archive changes nothing. The runtime takes the flat files over into the journal on the next
  mount.
- Exporting also works while the game is running, because it only reads committed files. If it hits a
  `Commit` exactly, it can fail; then export again. Importing only works while the program is not running.
- The page writes the ZIP code itself (writing stored, reading stored/deflate, CRC-32), without
  a third-party library. ZIP64 and encryption are rejected.

## Output and program end

- The page sets `Module.print`/`printErr` and `onExit` before loading the script. `exit code N` in the log is the
  signal for the tests (`tests/web/browser_test.mjs`).
- The program runs once per page load (the script is loaded on start). For a second run, reload the
  page; OPFS is preserved (`browser.opfs_storage` checks exactly that).

## Read speed via WasmFS OPFS (measured 2026-10-12, Mac M1)

- With the WasmFS OPFS backend **every** read or write call is a round trip to the OPFS worker (synchronous
  access handles exist only there). What matters is therefore the **number** of calls, not the amount of data.
- `std::fstream` (libc++ `basic_filebuf`) does not read a large range in one piece but fills its
  4 KiB buffer once per `underflow`. A read of 180 KiB thus became ≈ 45 round trips. Measured: ≈ 3 MB/s at
  game start (≈ 300 MB in ≈ 100 s), in Chromium as in Safari; there that was almost the entire start time.
- **Files opened read-only are read by WasmFS via `Blob.slice()`** (`opfs_backend.cpp`: `O_RDONLY` → Blob, `O_RDWR`
  → synchronous access handle). Every read is then an asynchronous read in the browser (milliseconds). Anyone who
  opens a file for writing even once gets the fast access handle for all accesses.
- Remedy (`platform/common/src/host_directory_storage.cpp`): all reads go through an unbuffered
  `FILE*` (`setvbuf(_IONBF)`), opened with `"r+b"` (on the desktop `"rb"` for read-only files);
  musl reads a range with one call. Writes still go through the stream, which flushes immediately, so the `FILE*`
  never sees stale data. Caution: access handles lock the file; while the game is running, the page
  cannot read the opened files itself.
- Result Chromium (real GPU, Mac): game start up to frame 64 first 43–66 s, with bundled large reads
  20 s, with access handles 10 s; first frame after 7 s (before 16–19 s).

## Tests

- `web.page_logic` (Node, every build): path mapping, what is left out, argv, save export (layout,
  ZIP round trip, deflate, broken archives, paths with `..`).
- `browser.save_backup` (WASM, Chromium headless): export via button as a download, import of the file, import of a
  deflate ZIP, a damaged ZIP leaves the saves unchanged.
- `browser.opfs_storage` (WASM, Chromium via Playwright): folder selection with a made-up dump including NSP,
  `prod.keys` and notes, copy to OPFS, check via `IStorage` (content by formula, read-only, nothing
  left-out present), write a save, journaled save with renamed folder committed and one
  change uncommitted; second page load: data and save still there, exactly the committed state in the journal.
- `browser.boot_basic_<nso|nro>`, `browser.boot_services_nso` (with `LGP_FIXTURE_IMPORT_DIR`): boot program in the browser
  on homebrew fixtures, module and RomFS from OPFS, comparison with the native Unicorn end state or the lines
  of `tests/boot/expected/services.txt`.

In CI the jobs `wasm` and `fixtures-wasm` install Playwright 1.56.1 with Chromium and xvfb; a separate
step fails if a browser test was skipped. For that the fixtures job additionally exports
`services_nso_lifted.cpp`.
